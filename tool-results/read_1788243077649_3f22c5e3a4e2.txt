    25→## Project Overview
    26→
    27→The Essay Writing Competition Management System is a full-stack web application designed to manage the complete lifecycle of essay writing competitions. It handles student registration, fee collection via Razorpay payments, PDF essay submission to Cloudinary, multi-examiner blind evaluation, automated score calculation, and result publication.
    28→
    29→**Key Capabilities:**
    30→
    31→- **Multi-role user management** — 5 distinct roles (SUPER_ADMIN, ADMIN, TEACHER, STUDENT, EXAMINER) with granular permission system
    32→- **Competition lifecycle** — Draft → Registration → Submission → Evaluation → Results → Completion
    33→- **Payment processing** — Razorpay integration with order creation, signature verification, and webhook handling
    34→- **Blind evaluation** — Configurable per competition; examiners evaluate without seeing student identity
    35→- **Multi-examiner scoring** — Configurable N examiners per essay with MEAN, MEDIAN, or TRIMMED_MEAN averaging
    36→- **Audit logging** — Immutable audit trail for all critical operations
    37→- **Real-time notifications** — In-app notification system for all user roles

   229→## Client-Side Architecture
   230→
   231→### SPA Routing via Zustand Nav Store
   232→
   233→The application uses a **single-page architecture** with no file-system routing. Instead of Next.js pages, the entire app lives at `/` and uses a Zustand store (`useNavStore`) to manage view switching:
   234→
   235→```
   236→User clicks sidebar item
   237→    ↓
   238→navigate('admin-dashboard')  →  useNavStore.currentView = 'admin-dashboard'
   239→    ↓
   240→AppShell re-renders → AppRouter switch statement
   241→    ↓
   242→Renders <AdminDashboardView /> with Framer Motion transition
   243→```
   244→
   245→The `NavView` type union defines all possible views (~35 views):
   246→
   247→| Prefix | Views | Role |
   248→|--------|-------|------|
   249→| `login`, `register`, `forgot-password` | 3 | Unauthenticated |
   250→| `admin-*` | 14 | SUPER_ADMIN, ADMIN |
   251→| `student-*` | 7 | STUDENT |
   252→| `teacher-*` | 5 | TEACHER |
   253→| `examiner-*` | 3 | EXAMINER |
   254→
   255→### Role-Based View Switching
   256→
   257→On authentication, the `AppShell` component auto-navigates to the correct dashboard based on the user's primary role:
   258→
   259→```typescript
   260→useEffect(() => {
   261→  if (isAuthenticated && user) {
   262→    const role = user.roles[0];
   263→    switch (role) {
   264→      case 'SUPER_ADMIN': case 'ADMIN': navigate('admin-dashboard'); break;
   265→      case 'STUDENT':      navigate('student-dashboard'); break;
   266→      case 'TEACHER':      navigate('teacher-dashboard'); break;
   267→      case 'EXAMINER':    navigate('examiner-dashboard'); break;
   268→    }
   269→  }
   270→}, [isAuthenticated, user]);
   271→```
   272→

   297→## Server-Side Architecture
   298→
   299→### API Route Pattern
   300→
   301→All API routes follow a consistent pattern:
   302→
   303→```
   304→POST /api/{resource}?action={verb}   → Action-based routing via query params
   305→GET  /api/{resource}?filter=value    → Query with optional filters + pagination
   306→PUT  /api/{resource}?action={verb}   → Update operations
   307→```
   308→
   309→**Action-based routing** is used instead of dynamic route segments (`[id]`). Each route file exports GET, POST, and optionally PUT handlers that internally dispatch to action handlers via `searchParams.get('action')`.
   310→
   311→```typescript
   312→// Typical route structure
   313→export async function POST(request: NextRequest) {
   314→  const action = new URL(request.url).searchParams.get('action');
   315→  switch (action) {
   316→    case 'create-order': return handleCreateOrder(request);
   317→    case 'verify':       return handleVerifyPayment(request);
   318→    case 'webhook':      return handleWebhook(request);
   319→    default:             return error(400, 'Invalid action');
   320→  }
   321→}
   322→```
   323→
   324→### API Route Registry
   325→
   326→| Route | GET | POST (actions) | PUT (actions) |
   327→|-------|-----|-----------------|---------------|
   328→| `/api/auth` | — | `login`, `register`, `verify-email` | — |
   329→| `/api/users` | List users | `create`, `update-role`, `toggle-active` | — |
   330→| `/api/competitions` | List (filter by status) | `create`, `update`, `update-status` | — |
   331→| `/api/registrations` | List (filter) | `create` | `cancel` |
   332→| `/api/payments` | List (filter) | `create-order`, `verify`, `webhook` | — |
   333→| `/api/essays` | List (filter) | Upload (multipart/JSON) | `validate` |
   334→| `/api/evaluations` | List (filter) | Save/submit evaluation | `calculate-result` |
   335→| `/api/examiners` | List | `create`, `assign`, `reassign` | — |
   336→| `/api/announcements` | List | `create`, `update`, `publish` | — |
   337→| `/api/notifications` | List (by user) | `mark-read`, `mark-all-read` | — |
   338→| `/api/dashboard` | Stats | — | — |
   339→| `/api/audit` | List (filter) | — | — |
   340→| `/api/settings` | List (by category) | `upsert` | — |
   341→
   342→### Middleware Layers
   343→
   344→Each API route applies the following checks in order:
   345→
   346→1. **Input parsing** — Extract `searchParams` and `request.json()` / `request.formData()`
   347→2. **Required field validation** — Check for missing required fields
   348→3. **Business rule validation** — Check status constraints, duplicates, eligibility
   349→4. **Database operations** — Prisma queries within `$transaction` where needed
   350→5. **Audit logging** — Create `AuditLog` entry after successful mutation
   351→6. **Notifications** — Create in-app `Notification` for relevant users
   352→7. **Response** — Return `{ success, data, message }` JSON
   353→
   354→### Service Abstraction
   355→
   356→Currently, business logic lives directly in route handlers. The pattern uses internal handler functions (`handleCreateOrder`, `handleVerifyPayment`, etc.) within each route file. There is no separate service layer, but the handler pattern provides clean separation within each file.

   360→## State Management
   361→
   362→### Zustand Stores
   363→
   364→Three Zustand stores manage all client-side state:
   365→
   366→#### 1. Auth Store (`useAuthStore`)
   367→
   368→- **Persistence:** `localStorage` via `persist` middleware (key: `essay-auth`)
   369→- **State:** `user: UserSession | null`, `isAuthenticated`, `isLoading`
   370→- **Actions:** `login()`, `logout()`, `updateUser()`, `setLoading()`, `hasRole()`, `hasAnyRole()`
   371→- **Purpose:** Manages user session, role checking, and authentication state
   372→
   373→#### 2. Nav Store (`useNavStore`)
   374→
   375→- **Persistence:** None (resets on page reload)
   376→- **State:** `currentView: NavView`, `sidebarOpen`, `breadcrumbs`
   377→- **Actions:** `navigate()`, `setSidebarOpen()`, `toggleSidebar()`, `setBreadcrumbs()`, `pushBreadcrumb()`
   378→- **Purpose:** SPA routing, sidebar toggle, breadcrumb trail
   379→
   380→#### 3. App Store (`useAppStore`)
   381→
   382→- **Persistence:** None
   383→- **State:** `notifications[]`, `unreadCount`
   384→- **Actions:** `setNotifications()`, `markAsRead()`, `markAllAsRead()`
   385→- **Purpose:** In-memory notification cache for the notification bell
   386→
   387→### Server State (TanStack Query)
   388→
   389→TanStack Query (`@tanstack/react-query`) is available for server state caching and synchronization. Individual view components use it for data fetching with automatic refetch, stale-while-revalidate, and optimistic updates.

   393→## Authentication Flow
   394→
   395→### Login
   396→
   397→```
   398→Student/Teacher/Admin
   399→    │
   400→    ▼
   401→POST /api/auth?action=login
   402→    │  { email, password }
   403→    │
   404→    ├─ User not found → 401 "Invalid email or password"
   405→    ├─ User inactive  → 403 "Account is deactivated"
   406→    ├─ Password invalid → 401
   407→    │
   408→    ▼
   409→User found, password valid
   410→    │  • Fetch roles, profiles
   411→    │  • Create audit log (USER_LOGIN)
   412→    │  • Return session data
   413→    │
   414→    ▼
   415→Client: useAuthStore.login(sessionData)
   416→    │  • Persist to localStorage
   417→    │  • Auto-navigate to role dashboard
   418→```
   419→
   420→### Registration
   421→
   422→```
   423→POST /api/auth?action=register
   424→    │  { email, password, name, role, ...profileFields }
   425→    │
   426→    ├─ Validate required fields
   427→    ├─ Check email uniqueness → 409 if exists
   428→    ├─ Password min 6 chars → 400
   429→    ├─ Create User + UserRole + Profile (in transaction)
   430→    ├─ Create audit log (USER_REGISTER)
   431→    │
   432→    ▼
   433→Return { id, email, name, role }
   434→```
   435→
   436→### Email Verification
   437→
   438→```
   439→POST /api/auth?action=verify-email
   440→    │  { token }
   441→    │
   442→    ├─ Find EmailVerificationToken
   443→    ├─ Check not used, not expired
   444→    ├─ Mark user.emailVerified = true
   445→    ├─ Mark token.usedAt = now (transaction)
   446→    ├─ Create audit log (EMAIL_VERIFIED)
   447→    │
   448→    ▼
   449→Return success
   450→```
   451→
   452→### Session Management
   453→
   454→The system uses a **client-side session** pattern:
   455→
   456→1. Login returns full `UserSession` object (id, email, name, roles, profiles)
   457→2. Client stores session in `localStorage` via Zustand `persist`
   458→3. Each API request does **not** include session token (currently trust-based)
   459→4. On page load, Zustand hydrates from `localStorage`
   460→5. Logout clears the store and navigates to login
   461→
   462→> **Note:** This is a development-mode architecture. Production should add JWT tokens, HTTP-only cookies, or NextAuth.js session management.

   665→## Caching Strategy
   666→
   667→### Client-Side Caching
   668→
   669→| Layer | Technology | What's Cached | TTL / Invalidation |
   670→|-------|-----------|---------------|---------------------|
   671→| **Auth session** | Zustand + `persist` | User session, roles | Manual logout / localStorage clear |
   672→| **Navigation** | Zustand (no persist) | Current view, sidebar state | Page reload resets |
   673→| **Notifications** | Zustand (no persist) | Notification list, unread count | Refetch on view mount |
   674→| **Server data** | TanStack Query | API responses (competitions, users, etc.) | `staleTime`, `refetchOnMount`, `refetchOnWindowFocus` |
   675→
   676→### Server-Side Caching
   677→
   678→| Layer | Technology | What's Cached | TTL |
   679→|-------|-----------|---------------|-----|
   680→| **Database** | None (in-memory Prisma) | Connection pooling | Process lifetime |
   681→| **API responses** | None | — | — |
   682→| **Static assets** | Next.js built-in | CSS, JS, images | Immutable hashes |

   698→## Error Handling Architecture
   699→
   700→### API Response Contract
   701→
   702→All API responses follow a consistent envelope:
   703→
   704→```typescript
   705→interface ApiResponse<T = unknown> {
   706→  success: boolean;   // Operation result
   707→  data?: T;           // Response payload
   708→  error?: string;     // Error message (human-readable)
   709→  message?: string;   // Success message
   710→}
   711→```
   712→
   713→Paginated responses extend this:
   714→
   715→```typescript
   716→interface PaginatedResponse<T> extends ApiResponse<T[]> {
   717→  total: number;      // Total matching records
   718→  page: number;       // Current page (1-based)
   719→  pageSize: number;   // Items per page
   720→  totalPages: number; // Total pages
   721→}
   722→```
   723→
   724→### Error Handling Pattern
   725→
   726→Every API route wraps its handler in a try-catch:
   727→
   728→```typescript
   729→export async function POST(request: NextRequest) {
   730→  try {
   731→    // ... business logic
   732→  } catch (error: unknown) {
   733→    const message = error instanceof Error ? error.message : 'Internal server error';
   734→    return Response.json({ success: false, error: message }, { status: 500 });
   735→  }
   736→}
   737→```
   738→
   739→### HTTP Status Codes
   740→
   741→| Code | Usage |
   742→|------|-------|
   743→| `200` | Successful GET / PUT |
   744→| `201` | Successful POST (created) |
   745→| `400` | Bad request (missing fields, invalid state, business rule violation) |
   746→| `401` | Unauthorized (invalid credentials) |
   747→| `403` | Forbidden (account deactivated, insufficient permissions) |
   748→| `404` | Not found (entity doesn't exist) |
   749→| `409` | Conflict (duplicate email, duplicate registration) |
   750→| `500` | Internal server error (uncaught exception) |
   751→
   752→### Client Error Display
   753→
   754→- **Toast notifications** via `sonner` for action feedback (success, error, warning)
   755→- **Form validation errors** displayed inline via React Hook Form + Zod
   756→- **API errors** caught in view components and displayed as toast messages

   760→## Background Jobs Architecture
   761→
   762→### Current State
   763→
   764→The system does **not** currently use a background job queue. All operations are synchronous within API request handlers. This includes:
   765→
   766→- Email sending (planned — currently in-app notifications only)
   767→- File upload to Cloudinary (currently mocked)
   768→- Result calculation (triggered manually by admin)
   769→- Notification dispatch (created synchronously in DB)
   770→
   771→### Planned Background Jobs
   772→
   773→For production, the following should be migrated to a job queue:
   774→
   775→| Job | Trigger | Implementation Option |
   776→|-----|---------|----------------------|
   777→| Welcome email | User registration | Resend API + Vercel Cron / BullMQ |
   778→| Payment confirmation email | Payment success | Webhook → email queue |
   779→| Essay validation | Essay upload | File processing queue |
   780→| Result notification | Result publication | Batch notification job |
   781→| Registration reminder | Scheduled | Vercel Cron Job |
   782→| Deadline notifications | Scheduled | Vercel Cron Job |
   783→| Bulk result calculation | Admin action | Queue + progress tracking |
   784→
   785→### Recommended Architecture
   786→
   787→```
   788→API Route
   789→    │
   790→    ├─ Fast path: Create DB record, return immediately
   791→    │
   792→    └─ Async path: Push to job queue
   793→          │
   794→          ▼
   795→    ┌─────────────┐
   796→    │ Job Queue    │  (BullMQ / Inngest / Trigger.dev)
   797→    │ (Redis/DB)   │
   798→    └──────┬──────┘
   799→           │
   800→           ▼
   801→    ┌─────────────┐
   802→    │  Worker      │  Process jobs: email, file ops, calculations
   803→    └─────────────┘
   804→```
   805→
   806→For Vercel serverless deployment, **Inngest** or **Trigger.dev** are recommended as they integrate natively without requiring a persistent Redis instance.
